# Spec 8 — Alpha pública

Fecha: 2026-10-30. Estado: **aprobada por el usuario el 2026-10-30**; sin plan todavía. Roadmap: `docs/tsuki/ROADMAP.md`,
sección 3 ("Definición de la Alpha") y sección 8 ("Después de la Alpha"), de la que esta spec adelanta casi todo.
Depende de: Specs 1a a 7, todas cerradas.

Marcas: **[V]** comprobado el 2026-10-30; **[D]** decisión del usuario (conversación del 2026-10-30); **[P]**
decisión del autor de la spec, que el usuario puede revisar al aprobarla.

## 1. Objetivo

Dejar todo listo para que el usuario publique la Alpha en un repositorio de GitHub nuevo: un port que un jugador
pueda bajar, instalar y jugar hasta el título del capítulo 1, con un launcher que reconozca su dump y documentación
que describa este proyecto y no el juego anterior.

No hay más trabajo de emulación: las Specs 2 a 6 cubrieron el kernel, los servicios, el audio, el vídeo, el 2D, el
ratón y los saves. Lo que queda es:
- marcar los criterios de la Alpha;
- llevar Windows hasta un build cruzado con exit code 0, probado con Wine;
- arreglar el launcher y el empaquetado, rotos desde la Spec 1a;
- reescribir los README;
- dejar documentada la estética, que se cambia antes de publicar.

- **[D]** Windows entra en la Alpha. Como mínimo, el build termina con exit code 0. Se compila desde Linux y no en un

## 4. Bloque A — Windows: build cruzado y Wine

### A1. Cadena de compilación

- **[P]** El compilador es **llvm-mingw**: una release de GitHub con versión fija, para host Linux x86_64 y UCRT.
  Tiene el mismo ABI que MSYS2 CLANG64 (clang, libc++, UCRT).
- **[P]** El sysroot son **los paquetes de MSYS2 CLANG64** de `packaging/windows/README.md`, con sus dependencias,
  bajados de `repo.msys2.org` y extraídos. Son los mismos binarios que usa un build nativo.
- Todo vive en una carpeta sin versionar: **[P]** `out/cross/`. No se instala nada en el host ni en la distrobox.
  Si hace falta algún paquete del sistema en la distrobox (por ejemplo `zstd`, que ya está), se documenta en
  `docs/ENTORNO.md`.
- Un script **[P]** `tools/cross_windows_env.sh` baja la cadena y el sysroot con versiones fijas y comprueba sus
  sumas. Debe poder repetirse sin volver a bajar lo que ya está.
- Un archivo de toolchain de CMake para el build cruzado: **[P]** `packaging/windows/cross-toolchain.cmake`.
- **[P]** `build.sh --windows` hace el build cruzado desde Linux. Sin la opción, `build.sh` se comporta como hoy, y
  en MSYS2 tampoco cambia nada.
- Las herramientas que el build ejecuta en el host (por ejemplo, la compilación de shaders de shadPS4 o los
  scripts de Python) usan las de Linux, no las del sysroot.

**Hecho, A1 (tarea 1 del plan, 2026-10-31):** la cadena y el toolchain; `build.sh --windows` es la tarea 2.
- `tools/cross_windows_env.sh` llena `out/cross/` (~2,6 GB, sin versionar):
  - `llvm-mingw/`: llvm-mingw **20261020** (`ucrt-ubuntu-22.04-x86_64`), con LLVM 23.1.4, la misma versión que el
    `clang` de MSYS2 CLANG64 ese día. Así las DLL de MSYS2 cargan con el `libc++.dll` y el `libunwind.dll` de
    llvm-mingw.
  - `sysroot/clang64/`: **134 paquetes** de `repo.msys2.org`. Las raíces son las bibliotecas de
    `packaging/windows/README.md` (vulkan-headers, vulkan-loader, vulkan-memory-allocator, sdl3, fmt, boost, robin-map,
    xxhash, ffmpeg, zydis, spirv-tools, spirv-headers, spirv-cross); el resto son dependencias, sobre todo del ffmpeg
    de MSYS2 (códecs, glib2, cairo, python, tk…), las mismas que instala un build nativo.
  - Quedan fuera las herramientas del README (toolchain, cmake, ninja, pkgconf, python, glslang), porque el build usa
    las de Linux, y los paquetes que ya trae llvm-mingw (crt, headers, winpthreads, libwinpthread, libc++, libunwind,
    compiler-rt): sus headers en el sysroot taparían los del compilador.
  - Versiones fijas: las de llvm-mingw en el script y las de MSYS2 en su lista `LOCK` (archivo y SHA256 de cada
    paquete). `--update-lock` la regenera desde `clang64.db`. Cada descarga se comprueba con su suma.
- `packaging/windows/cross-toolchain.cmake`: compiladores, `windres`, `ar` y `ranlib` de llvm-mingw. Bibliotecas,
  headers y paquetes de CMake solo del sysroot; programas solo de Linux; `pkg-config` de Linux con
  `PKG_CONFIG_LIBDIR`/`PKG_CONFIG_SYSROOT_DIR`.
  - Añadido respecto al plan: `sysroot/clang64/include` y `sysroot/clang64/lib` son búsquedas por defecto, como
    `/clang64/include` y `/clang64/lib` en el clang de MSYS2. Sin ello, el paquete CMake de Zydis enlaza un
    `-lZycore` sin ruta y falla.
  - CMake resuelve una ruta relativa de `CMAKE_TOOLCHAIN_FILE` desde la carpeta de build. La tarea 2 la pasa
    absoluta (`$PWD/packaging/...`).
- Comprobado:
  - Dos pasadas del script en la distrobox, exit 0 las dos. La primera bajó los 135 componentes en 4 min 15 s; la
    segunda dijo «ya estaba» en los 135 y tardó 0,6 s.
  - `x86_64-w64-mingw32-clang hello.c` da `PE32+ executable for MS Windows 6.00 (console), x86-64`. `file` está en
    el host, no en la distrobox.
  - Un proyecto CMake de prueba (`out/cross-check/`, sin versionar) encuentra con el toolchain todo lo que pide
    `gpu/CMakeLists.txt`: Vulkan, fmt, Boost, tsl-robin-map, VMA, Zydis, y por `pkg-config` xxhash, SDL3 y ffmpeg. El
    `glslang` que encuentra es `/usr/bin/glslang`. Enlaza un `.exe` contra UCRT (`api-ms-win-crt-*`), `libc++.dll`,
    `SDL3.dll` y `avcodec-63.dll`.
  - `cmake -S gpu` con el toolchain, `TSUKI_PGO=off` y `TSUKI_LTO=OFF` configura con exit 0. Da los mismos avisos de
    política (Boost, miniz) que el build nativo. Compilarlo es la tarea 2.
- No hizo falta ningún paquete nuevo en la distrobox (`curl`, `tar`, `xz`, `zstd`, `sha256sum` y `python3` ya
  estaban). Comandos en `docs/ENTORNO.md` §8.

### A2. Prueba con Wine

- Se usa el Flatpak `org.winehq.Wine` a través de `flatpak-spawn --host flatpak run org.winehq.Wine …`.
  - El prefijo va en una carpeta sin versionar, **[P]** `out/wine-prefix/`.
  - Las DLL salen del sysroot: junto al `.exe`, o con `WINEPATH`.
  - Si el sandbox del Flatpak no ve el repo o el dump, se le da acceso con `--filesystem` en la línea de comandos,
    sin cambiar los permisos globales. **[P]** Si Wine del Flatpak no sirve, se usa el GE-Proton 11-3 a través de
    `umu-run`; se documenta cuál se usó.
- Pasos, en orden:
  1. `tsuki-gpu-capabilities.exe` lista la RX 6650 XT a través de winevulkan (con RADV por debajo).
  2. `tsuki-probe.exe --vulkan-only` termina bien.
  3. `tsuki-probe.exe <boot-linked.bin> --app0 <dump> --check-imports` lista las mismas 3 trampas que en Linux.
     El `boot-linked.bin` se prepara con `run.py`, o con los scripts de `scripts/` desde Linux, porque el formato es
     el mismo.
  4. El juego arranca bajo Wine hasta el menú de título, con música. El loader de Windows depende de vistas
     placeholder (`VirtualAlloc2`/`MapViewOfFile3`) y del TCB en un slot de TLS del TEB accedido por `gs:`, y Wine
     puede no imitar esto igual que Windows. Por eso **[P]** este paso se intenta siempre, pero un fallo propio de
     Wine (el mismo `.exe` no falla en Windows real) se documenta con su error y no bloquea: lo que decide es la
     prueba en Windows real (§8, "Antes de publicar").

### A3. Paquete de Windows

- El paquete de Windows entra en la release **[D]**, así que `packaging/windows/package.sh` tiene que generarlo.
- **[P]** Se intenta desde Linux, con el build cruzado y un Python de python.org instalado en el prefijo de Wine para
  PyInstaller. Si PyInstaller no funciona bajo Wine, se documenta el error y el paquete se genera en el PC con
  Windows del usuario, con el `build.sh` de MSYS2 de siempre.
- El `Tsukihime.exe` congelado abre el launcher bajo Wine y reconoce el dump.

## 5. Bloque B — Launcher y empaquetado

Adelanta casi toda la sección 8 del roadmap, "Launcher, empaquetado y documentación de usuario".

- **Reconocer el dump.** El launcher y `run.py` reconocen CUSA47999 por su `param.sfo` (`TITLE_ID`), sin
  `patches.game_profile`.
  - **[P]** La identidad del juego (serial y título) vive en un solo lugar, que comparten `run.py`, el launcher y
    el empaquetado. `src/probe.c` ya solo arranca CUSA47999 (código 30).
- **Quitar la elección de parches por nombre del juego anterior:**
  - `EXCLUSIVE_PREFIX` en `scripts/patches.py`, que el launcher importa;
  - lo correspondiente en `scripts/graphics_options.py`;
  - el aviso de `run.py` sobre el parche de frame rate;
  - el menú del juego, sus ajustes y sus tests.
  - La lectura de XML de terceros (shadPS4/GoldHEN) de `scripts/patches.py` **se queda**: es genérica.
- **Quitar del launcher las opciones de funciones borradas.** Cualquier resto de cheats, orbes, multiplicadores,
  barra de vida o upscalers temporales que quede en textos, ajustes o páginas. Se inventaría primero con `grep`, y
  la lista va en los resultados.
- **Controles.** "Touchpad right" ya no muestra `Backspace`/`back` como teclas por defecto.
- **Código 30.** El launcher da un mensaje propio, del tipo "este build solo ejecuta TSUKIHIME (CUSA47999)", en vez
  de un error genérico.
- **Tests.** Los 4 tests de §3 pasan, y se quitan sus `expectedFailure`.
  `python3 -m unittest discover -s tests` termina sin fallos ni éxitos inesperados.
- **Empaquetado.**
  - Se quita `cp -r patches` de `packaging/linux/build.sh` y de `packaging/windows/package.sh`.
  - `packaging/linux/build.sh` genera el AppImage con exit code 0.
  - El AppImage abre el launcher, que elige el dump y arranca el juego hasta el menú de título.
- **Nombre público: "Project Blue Moon"** **[D]**. Lo que el jugador ve como nombre del port pasa a "Project Blue
  Moon":
  - `APP_NAME` del launcher (`launcher/tsuki_launcher_win.py:46`): el título de la ventana, la cabecera y los
    diálogos;
  - `Tsukihime.exe` y `Play Tsukihime.exe` (`packaging/windows/package.sh`, `play.c`), y `Tsukihime.lnk`;
  - el `Name=`/`Comment=` de `packaging/linux/tsuki.desktop` y la entrada que escribe el launcher (líneas 612 y 2008);
  - los nombres de los paquetes: `dist/tsuki-x86_64.AppImage` y `dist/tsuki-windows.zip`. **[P]** Pasan a
    `project-blue-moon-x86_64.AppImage` y `project-blue-moon-windows.zip`;
  - el acceso de Steam.
  
  Siguen nombrando el juego, porque describen qué dump hace falta y no son el nombre del port: los textos que piden
  el dump ("TSUKIHIME -A piece of blue glass moon- (CUSA47999)", líneas 1215-1217) y el título de la ventana del
  juego, que sale del `param.sfo` del propio dump. **[P]** No cambian los nombres internos (`tsuki_*`, `TSUKI_*`,
  `tsuki-probe`, `libtsukigpu.so`, `tsuki.ini`, la marca `tsuki:`): son de la Spec 7 y el jugador no los ve como nombre
  del producto. Tampoco se migran las carpetas de ajustes de una versión anterior: no hay ninguna publicada.
- **Prueba del usuario.** En Linux, el usuario abre el launcher, elige el dump, juega y cierra. El launcher debe
  mostrar la portada y el serial correctos.

- **Lo que cuentan los README:**
  - un port nativo de TSUKIHIME -A piece of blue glass moon- (PS4, CUSA47999 v01.00), solo en inglés;

- **URL del repositorio.** Todavía no existe, así que los enlaces a Releases e Issues usan un único marcador que el

- **`.github/ISSUE_TEMPLATE/`** se adapta a Tsukihime: serial CUSA47999, el log `user/last_run.log` y las

- **Árbol público.** Se repasa `git ls-files` en busca de cualquier cosa que no deba publicarse: archivos del juego,

  en ese caso se para y se pregunta.
- **`CLAUDE.md`, sección "Conventions":** `tsuki/main` es la rama principal y `main` es histórica. Ya no se dice que
  `main` recibe las fusiones probadas.

## 8. Criterios de aceptación

**Cierre técnico de la spec**

- [ ] Criterios de la sección 3 del roadmap marcados, cada uno con su evidencia:
  - el prólogo se da por aprobado **[D]**;
  - idioma, saves, controles y render 2D, con la evidencia de la Spec 6;
  - un log sin `STOP:` ni `Fault:`, en un recorrido repetido al final de esta spec (`tools/route.sh replay`);

- [ ] `bash build.sh --windows` termina con exit code 0 desde la distrobox y genera `tsuki-probe.exe` y
  `tsuki-gpu-capabilities.exe`.
- [ ] Bajo Wine, `tsuki-gpu-capabilities.exe` ve la RX 6650 XT, `--vulkan-only` pasa y `--check-imports` da las 3
  trampas de Linux. Si algo de esto no sale, queda documentado con el error y con el plan de probar en un PC con
  Windows.
- [ ] `bash build.sh --test` en verde. `python3 -m unittest discover -s tests` sin fallos y sin `expectedFailure`
  en los tests del launcher. `tools/check_rename.sh` también cubre los README.
- [ ] El launcher reconoce CUSA47999 y arranca el juego desde el código fuente y desde el AppImage. El usuario lo
  confirma.
- [ ] `packaging/linux/build.sh` termina con exit code 0, y `packaging/windows/package.sh` genera el `.zip` (desde
  Linux con Wine o, si no sale, en el PC con Windows del usuario).
- [ ] El recorrido grabado (`out/baseline/6a/`) y los fotogramas oráculo del arranque salen iguales después de los
  cambios de `run.py` y del launcher.
- [ ] `README.md`, `README.es.md` y `README-Windows.txt` describen este proyecto. `README.pt-BR.md` ya no existe.
- [ ] El roadmap tiene una fila para la Spec 8 y la sección "Fuera de la Alpha" ya no excluye Windows. La sección 8
  ("Después de la Alpha") conserva solo lo que no se hizo aquí. `CLAUDE.md` está al día.

**Antes de publicar (los cumple el usuario; la spec solo los lista)**

- [ ] Fuente, paleta e icono cambiados (§7).
- [ ] El repositorio de GitHub existe y el marcador `https://github.com/OWNER/REPO` está sustituido en los README y
  en `.github/`.
- [ ] El usuario prueba el `.zip` en Windows real: el launcher reconoce el dump y el juego llega al menú de título
  con música y guarda. Si falla, se arregla antes de publicar.
- [ ] Release subida por el usuario con el AppImage y el `.zip` de Windows.

## 10. Riesgos

| Riesgo | Mitigación |
|---|---|
| El build cruzado no encuentra alguna dependencia en el sysroot de MSYS2 (dependencias transitivas, rutas absolutas de `pkg-config` o de CMake que apuntan a `/clang64`) | Corregir los prefijos en el toolchain y en `PKG_CONFIG_SYSROOT_DIR`.
